# Control research — first-time setup

**What this is:** a **closed-loop control testbed** on the LIMO. OptiTrack gives
the robot's true position; a **swappable controller** (P / PID / LQR, later MPC /
DeePC / Koopman) computes velocity commands; the commands go straight to
`/cmd_vel`. **Nav2 is bypassed**: this replaces Nav2's controller so control laws
can be compared on a drift-free plant.

**Why bypass Nav2:** Nav2 = planner + controller + costmaps. This model replaces
only the **controller**. There is no planner and no obstacle avoidance: the robot
drives straight at the goal. That's intentional, because obstacles would
confound a controller comparison. Closing the loop on mocap means the state
estimate is sub-millimeter and drift-free, so any tracking error belongs to the
*controller*, not the estimator. That's the clean testbed.

This page is the one-time setup. The per-session run is in
[`CONTROL_DAILY.md`](CONTROL_DAILY.md).

## 1. Put the MATLAB folders on the path

Nothing needs copying: the MATLAB code lives in the repo, under `matlab/`:

| File | Folder | Role |
|---|---|---|
| `limo_ctrl_params.m` | `control/` | Parameters + gain design (LQR) |
| `build_limo_control_model.m` | `control/` | Builds `limo_mocap_control.slx` programmatically |
| `limo_connect.m` | `goals/` | MATLAB ↔ robot connection (correct QoS + domain + TF + status) |
| `limo_state.m` | `goals/` | Read the full robot state |
| `limo_goal.m` | `goals/` | Send one Nav2 goal |
| `limo_lidar_obstacle.m` | `perception/` | Nearest obstacle + sector clearance from `/scan` |
| `analyze_runs.m` | `analysis/` | Offline bag comparison |

Add them to the path once (adjust `~/limo` if you cloned elsewhere):

```matlab
addpath('~/limo/matlab/control','~/limo/matlab/goals', ...
        '~/limo/matlab/perception','~/limo/matlab/analysis'); savepath
```

Keep **one** copy of each function on the path. If an older copy (for example in
`~/matlab_limo/`) is also on the path, MATLAB silently runs whichever comes
first. Check with `which -all limo_connect`.

**Why a build *script* and not a committed `.slx`:** the model is generated by
code (`add_block`/`set_param`). That makes it diff-able and version-controlled,
and every fix is reproducible: run one script and you get the model. The
generated `limo_mocap_control.slx` is git-ignored; **rebuild it whenever
`build_limo_control_model.m` changes**.

## 2. Understand the model before running it

Signal flow, left to right:

```
/vrpn_mocap/Limo/pose ─► Subscribe ─► Bus Selector ─► quat2yaw
                                            │
                                   state = [x; y; θ]
                                            │
   goal = [xd; yd; θd] ──────────►  ┌───────────────────┐
                                    │ Variant Subsystem │   ← swap controller
                                    │  P │ PID │ LQR    │
                                    └───────────────────┘
                                            │  u = [v; ω]
                                     Saturate → E-STOP
                                            │
              Blank Twist ─► Bus Assignment ─► Publish /cmd_vel
```

**The Variant Subsystem is the whole point.** All controllers share ONE
interface: `in: state[3], goal[3] → out: u=[v;ω]`. Set `CTRL = 1|2|3` to swap.
To add MPC / DeePC / Koopman later: add `V_MPC = Simulink.Variant('CTRL==4')`,
copy a choice subsystem, and replace one MATLAB Function body. Nothing else
changes.

## 3. The DDS fix (one-time file, used every session)

**Why MATLAB can't see the container's topics without it:** Fast DDS uses
**shared memory** between processes on the same host. The container runs as
**root** and creates `/dev/shm/fastrtps_*` segments that MATLAB (running as your
user) can't open. Result: MATLAB sees the *robot* (UDP, remote) but not the
*container* (`vrpn_mocap`, Nav2). The fix is to force **UDP-only** transport on
both sides.

The profile is [`config/fastdds_udp.xml`](../config/fastdds_udp.xml), copied to
`~/maps/fastdds_udp.xml` in DEVICE_SETUP step 6. Its content, for reference:

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<profiles xmlns="http://www.eprosima.com/XMLSchemas/fastRTPS_Profiles">
  <transport_descriptors>
    <transport_descriptor>
      <transport_id>udp_only</transport_id>
      <type>UDPv4</type>
    </transport_descriptor>
  </transport_descriptors>
  <participant profile_name="udp_participant" is_default_profile="true">
    <rtps>
      <userTransports><transport_id>udp_only</transport_id></userTransports>
      <useBuiltinTransports>false</useBuiltinTransports>
    </rtps>
  </participant>
</profiles>
```

Make it permanent on both sides so you stop doing it by hand.

Container (skip if DEVICE_SETUP step 5 already added it):

```bash
grep -q FASTRTPS_DEFAULT_PROFILES_FILE /root/.bashrc || \
  echo 'export FASTRTPS_DEFAULT_PROFILES_FILE=/root/maps/fastdds_udp.xml' >> /root/.bashrc
```

MATLAB: create `startup.m` in `~/Documents/MATLAB/` (runs at every MATLAB start):

```matlab
setenv("FASTRTPS_DEFAULT_PROFILES_FILE", fullfile(getenv('HOME'), "maps", "fastdds_udp.xml"));
```

The variable is read once, when MATLAB's ROS stack first starts. If you set it by
hand, do it **before creating any `ros2node`**, or restart MATLAB.

Container shells that were already open when you changed `.bashrc` keep the old
setting. Restart them (and `ros2 daemon stop`).

## 4. Build the model once

```matlab
limo_ctrl_params            % loads P, CTRL, variant objects; prints the LQR gain K
build_limo_control_model    % builds + saves + opens limo_mocap_control.slx
```

**LQR gain design.** `limo_ctrl_params` designs the gain with
`K = lqr(A, B, Q, R)` on the body-frame unicycle error dynamics, linearized about
a forward speed `v0 = 0.25 m/s`. With the default `Q`/`R` that gives
`K = [-2 0 0; 0 -4 -2.4495]`. The gain is baked into the LQR block at build time,
with no manual pasting.

Tune the trade-off with `Q` (state penalty) and `R` (effort penalty) in the
params file, then **rebuild**. Bigger `Q` → tighter tracking, more aggressive;
bigger `R` → gentler, less effort. Without the Control System Toolbox,
`limo_ctrl_params` warns and falls back to the precomputed K above, which does
**not** follow edits to `Q`, `R` or `v0`.

(Historical note: before the toolbox was installed, this was solved by hand via a
Hamiltonian eigendecomposition of `H = [A, -B R⁻¹ B'; -Q, -A']`. Same result.)

**The programmatic build is release-sensitive.** The script verifies each block
parameter it sets and stops with a message naming the block and field if one
didn't take. Set that field by hand in the block dialog, then re-run. The
known-tricky ones (already handled): QoS parameter names are UPPERCASE
(`QOSReliability`); Subscribe **port 2** is the message bus (port 1 is `IsNew`);
bus signals must be assigned **after** an Update Model.

## 5. Configure the model's ROS network (once per model)

In the model: **Simulation → ROS Toolbox → ROS Network**

- Domain ID: **10**
- RMW: **rmw_fastrtps_cpp**

Then double-click **Mocap Pose** and confirm **Reliability = Best effort**,
**Durability = Volatile**.

**Why best-effort:** a best-effort subscriber matches both best-effort and
reliable publishers; a reliable subscriber won't match a best-effort one and
receives nothing. Sensor streams (mocap, `/scan`, `/tf`) are always subscribed
best-effort in this project.

## 6. First smoke test (the robot must NOT move)

1. Robot drivers + `vrpn_mocap` running (see the [daily manual](CONTROL_DAILY.md)).
   **Nav2 stopped.**
2. Press **Run**.
3. The robot should **not** move: the E-STOP Manual Switches start in the
   **zero** position.
4. **Push the robot by hand**: the `x`, `y`, `theta` displays should track it.

If the displays track the robot, mocap → Simulink works. You're one double-click
(the E-STOPs) away from live control. Do the first *moving* run slowly; see the
daily manual's safety section.

## 7. Safety model (understand before enabling motion)

- **Two E-STOP Manual Switches** feed zero velocity by default. Motion only
  happens when you *double-click* them during simulation. Double-click again →
  instant stop.
- **Saturation blocks** clamp `v ≤ P.v_max`, `ω ≤ P.w_max`. First runs:
  `P.v_max = 0.15`.
- **Only one thing may publish `/cmd_vel`.** Stop Nav2 (and the wandering node)
  before running this model, or they fight over the robot.
- **Stopping the simulation is not an E-STOP.** Stopping the sim just stops
  publishing; the base may keep executing the last `/cmd_vel` it received. Always
  flip the E-STOPs to zero *before* pressing Stop. If the robot keeps rolling,
  send a zero command from a container shell:
  `ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist "{}"`

## 8. Analysis tools (Control System Toolbox): comparing controllers

Once you're comparing P / PID / LQR (and later MPC / DeePC), don't just eyeball
the XY trace; quantify it. The toolbox gives you:

| Function | Use |
|---|---|
| `step`, `impulse` | time-domain response of a linearized loop |
| `bode`, `nyquist` | frequency response |
| `margin` | gain/phase stability margins |
| `pole`, `eig`, `damp` | closed-loop poles, natural modes, damping |
| `care`, `dare` | Riccati solvers for custom optimal control |

These connect directly to eigenvalue / natural-mode / stability analysis: the
linearized error dynamics `A`, `B` in `limo_ctrl_params.m` are exactly what you
feed to `ss(A,B,C,D)`, then `step`/`bode`/`pole`.

**Fair comparison = same plant, same metric.** Every controller honors the same
interface and runs on the same drift-free plant, so compare them on identical
metrics: settling time, overshoot, RMSE-to-goal, control effort (∫|u|). Record
each run and compute offline, the same way as the nav comparison experiment:

```bash
# container, from /root/maps so the bag lands on the mounted folder:
cd /root/maps && ros2 bag record -o ctrl_lqr_run1 /vrpn_mocap/Limo/pose /cmd_vel /odom
```

The `extractPose` helper in `matlab/analysis/analyze_runs.m` shows how to pull
the mocap trajectory from a bag.
